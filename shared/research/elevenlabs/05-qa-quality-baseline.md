## A3. STT 오류율 · 자막
- **지표**: 한국어 CER(주), 숫자·고유명사 정확도, 없는 말 지어내기 건수. 화자 구분은 엔진에 기능이 있을 때만 잰다(1단계 3-2 DER).
- **채점 규칙**: 문장부호 제거, 공백 제거 후 CER. **숫자 표기를 하나로 맞춘 뒤 계산**한다.
  - 이유: "오후 3시"와 "오후 세시"는 같은 말이지만 그대로 비교하면 CER 7.1%, WER 20%가 나온다(`05-qa/work/audio_check.py`로 실측).
- **공개 데이터의 한계**: Zeroth·FLEURS는 깨끗한 낭독이라 실제 회의보다 쉽다. 그래서 회의 유사 세트를 따로 두고, 마지막에는 사용자 녹음으로 "요약에 쓸 수 있는가"를 사용자가 판단한다(나중에 요청).
- **자막 타이밍 정답**: 회의 유사 세트는 QA가 발화를 이어 붙여 만들므로 **각 발화의 시작·끝 시각을 정확히 안다.** 이 값을 정답 경계로 쓴다.
- **합격선 근거**: CER 7%는 100자에 7자를 고치는 수준이다. 회의 15%는 사람이 다듬는 초안 기준이다. 참고로 ElevenLabs 문서는 자사 Scribe v2의 한국어를 WER 10~20% 등급으로 분류한다(1단계 3-2).

## A4. TTS 알아듣기 쉬움 · 자연스러움
- **명료도(객관)**
  - 역전사: TTS 결과를 채택된 STT로 다시 받아쓰게 해 원문과 CER을 비교한다.
  - **FLEURS 한국어 문장을 TTS 입력으로 쓰면 같은 문장의 사람 녹음(CC BY 4.0)이 있다.** 그 사람 녹음의 역전사 CER을 빼서 STT 자체 오류를 없앤다.
  - 숫자·영문 문장은 사람 녹음이 없으므로 절대값으로 판정한다.
- **숫자·약어 읽기**
  - C3 보고서에는 %, 날짜, 순위, SEO·URL 같은 영문이 많다.
  - **Claude 정규화 전처리를 켠 경우와 끈 경우**를 따로 기록한다. 합격 판정은 운영 설정(켠 쪽)으로 한다.
- **청취(사용자 1명)**
  - 평가자가 1명이라 통계가 아니라 **사용자의 판단**이다. 그래서 평균과 함께 "외부에 내보낼 수 있다" 개수를 합격 조건으로 둔다.
  - 1차: 5문장(A7 채점표)
  - 본 판정: 20문장(A8)
- **객관 점검**: `audio_check.py wav` 결과로 A2 "TTS 객관" 행을 판정한다.

## A5. CPU 처리 시간 허용치
- **정의**: RTF = 처리 시간 ÷ 음성 길이(DevOps와 같은 정의).
- **측정 조건**: 이 PC, 다른 무거운 작업 없음. 모델 로드 시간(콜드/웜)과 스레드 수를 기록한다.
- **"PC를 쓰면서 돌릴 수 있는가"**: 스레드를 6~8개로 제한한 조건도 한 번 잰다. 처리 중에 브라우저가 멈추지 않는지는 사용자가 체감으로 확인한다.
- **STT 1시간 값**: DevOps는 30초·5분 실측을 환산하고, 가능하면 1시간을 1회 실측한다(DevOps `PLAN.md`). 환산값으로는 **조건부까지만** 판정한다. 합격 확정은 1시간 실측(또는 A2의 60분 연속 처리 행)으로 한다.
- **기준 출처**
  - TTS·STT·복제 기준은 기획팀 조정 규칙(`01-planning-internal-mvp.md` 3절)과 같다.
  - 모델 로드와 RAM 기준은 QA 제안이다. RAM 8GB는 15.5GB 중 OS와 브라우저 몫을 남긴 값이다.

## A6. 클로닝 화자 유사도 (화자 = 대표 1명)
- **정규화 화자 유사도**
  - 상한 = 대표의 다른 실제 녹음끼리의 SECS
  - 하한 = Zeroth 시험 화자(같은 성별) 녹음과 대표 녹음의 SECS
  - 정규화 유사도 = (생성 음성 SECS − 하한) ÷ (상한 − 하한)
  - 임베딩 모델이 바뀌어도 해석이 같도록 이렇게 정규화한다.
- **화자 검증 수락률**: 같은 임베딩 모델의 EER 임계값을 넘는 생성 문장 비율. EER은 Zeroth 시험 화자 10명으로 정한다.
- **사용자 녹음 전 1차 판정**: Zeroth 시험 화자 1명을 "대역 화자"로 쓴다. 참조 1분, 평가용 실제 발화는 그 화자의 다른 문장이다. 엔진의 복제 능력과 속도만 미리 본다. 최종 판정은 대표 본인 녹음으로 한다.
- **참조 길이 안내**: 10초 / 30초 / 1분 참조를 비교한다. 1분 대비 정규화 유사도 하락이 0.1 이하인 가장 짧은 길이를 사용 안내 권장값으로 쓴다.
- **필요한 것**: 화자 임베딩 모델 1개(상업 허용 라이선스, 백엔드 선정 → DevOps 설치)

3. STT 정확도와 TTS 역전사: 받아쓰기 결과와 정답 문장으로 `audio_check.py cer "<정답>" "<결과>"`를 계산한다.

    - small·medium은 환산값이 합격 범위(≤30분)다. 다만 A5에 따라 환산값으로는 **조건부까지만** 판정한다. 회의 유사 30분 파일이나 60분 실측으로 합격을 확정한다.

### A7-2. TTS 역전사 판정 (2026-11-21)
- **방법**: DevOps가 faster-whisper small(int8)로 L1~L5를 다시 받아쓴 결과(`results/fw_small_backtx/`)를 원문과 비교했다. 숫자 표기를 맞춘 뒤 계산했다(QA 계산이 정본, DevOps 회신 합의). 문장 5개짜리 비교라 표기 같은 것 3쌍("일곱 시=7시", "두 시간=2시간", "세 가지=3가지")만 명시해서 맞췄다.
- **결과**

| 문장 | MeloTTS 받아쓰기 | Supertonic 받아쓰기 |
|---|---|---|
| L1 | …갓 구운 **밤**을… (CER 3.8%) | 정확 |
| L2 | 정확 | 정확 |
| L3 (12%, 1,284명) | …지난주보다 **1%** 늘어난 **일 284명**… (숫자 2개 모두 틀림) | …12% 늘어난 **1024명**… (1개 틀림) |

| L5 | 정확 | 정확 |
| **합계** | CER 4.4%, 숫자·약어 5/8(62.5%) | CER 1.5%, 숫자·약어 7/8(87.5%) |

- **A2 대입**
  - 역전사 CER: 둘 다 합격(≤8%).
  - 숫자·약어 정답률: 둘 다 조건부 하한(90%)에 못 미친다. 다만 A2의 합격 판정은 **운영 설정(Claude 정규화 켬)** 기준이고, 이번 샘플은 원문을 정규화 없이 넣은 것이다 → **"정규화 끈 조건"의 기록**으로만 남긴다.
- **해석**
  - Melo L3의 문장 안 0.82초 쉼은 3.84~4.66초 구간이다. 위치상 "1,284" 부근이고, 받아쓰기 "일 284명"과 맞아떨어진다. 천 단위 쉼표를 쉼으로 읽었을 가능성이 높다. 단어 단위 시각이 없어 확정하지는 못했다.
  - Melo L4의 "SEO" → "15"는 영문 약어를 제대로 읽지 못했을 가능성이 있다.
  - 단, 받아쓰기 모델이 가장 작은 small이라 오류 일부("빵→밤", "1284→1024")는 STT 쪽 실수일 수 있다 → 사용자 청취(R1-06·R1-11·R1-12·R1-02)로 가린다.
- **정규화 요구사항(백엔드·기획에 전달)**: TTS에 넣기 전에 Claude 정규화 단계에서 다음을 반드시 한다.
  - ① 숫자를 한글 읽기로 바꾸고 **천 단위 쉼표를 없앤다**(1,284 → 천이백팔십사)
  - ② % → 퍼센트
  - ③ 영문 약어를 한글 읽기로 바꾼다(SEO → 에스이오)
  - ④ 단위·조사가 붙은 숫자(72점, 2시간)는 문맥에 맞는 수사로 읽는다(칠십이 점, 두 시간)
- **다음 측정(가벼움)**: 정규화한 문장으로 두 엔진의 L3·L4만 다시 생성하고 small로 역전사한다(TTS 4개 + STT 4개). QA가 정규화본을 준비했다.
  - L3n: 이번 주 방문자는 지난주보다 십이 퍼센트 늘어난 천이백팔십사 명입니다.
  - L4n: 홈페이지의 에스이오 점수가 칠십이 점에서 팔십오 점으로 올랐습니다.
  - 숫자·약어 정답률이 이 정규화본으로 90% 이상이면 해당 행을 "운영 설정 기준"으로 판정한다.
- **정규화본 결과(2026-11-22, DevOps §2.1)**
  - 두 엔진 모두 L3n·L4n 역전사가 "…12% 늘어난 1284명", "SEO 점수가 72점에서 85점"으로 숫자·약어를 정확히 되살렸다.
  - 숫자 표기를 맞춘 CER은 L3n 0.0%다. L4n 13.8%는 "SEO"와 "에스이오"의 표기 차이뿐이다.
  - L1·L2·L5의 숫자(7시, 2시간, 3가지)는 원래 맞았다.
  - 숫자·약어 정답률(운영 설정 = 정규화 켬)은 **MeloTTS 8/8, Supertonic 8/8 = 100% → A2 "숫자 읽기" 행 합격(두 엔진 모두)**.
  - 남은 TTS 문제는 숫자가 아니라 **자연스러움(청취)** 이다.

### 1-2. 측정법 [제안]
1. **MOS(절대 평가)**: ITU-T P.800 ACR 방식 5점 척도(1 나쁨 ~ 5 아주 좋음) [외부 표준].
   - 청취자: 언어별 원어민 **20명 이상**, 헤드폰, 조용한 곳. 크라우드소싱이면 주의력 확인 문항(일부러 망가뜨린 음성)을 넣고 틀린 사람은 뺀다.
   - 문장: 시스템당 **40문장 이상**(3절 세트의 MOS 부분집합), 문장당 평가 **10개 이상**.
   - 같은 시험에 **사람 녹음(상한 기준)** 과 **일부러 낮춘 음성(하한 기준)** 을 섞어 척도를 고정한다.
   - 보고: 평균과 95% 신뢰구간. 시스템 이름은 숨기고 순서는 무작위.
2. **CMOS(상대 평가, 판정용)**: 같은 문장의 우리 음성과 ElevenLabs 음성을 나란히 들려주고 −3 ~ +3으로 고른다. MOS보다 적은 인원으로 작은 차이를 잡는다. **"ElevenLabs 수준" 판정은 CMOS를 주 지표로 한다.**
3. **역전사 이해도**: 생성 음성을 고정된 STT 엔진 1개로 다시 받아 적어 원문과 비교한다. 한국어 CER, 영어 WER. 발음 붕괴·누락·반복을 자동으로 잡는다. 두 시스템 모두 같은 STT로 재야 공정하다.
4. **정규화 오류율**: 3절 "숫자·날짜·금액·단위" 묶음에서 사람이 읽기 정답(예: "3시 30분" → "세 시 삼십 분")과 다르게 읽은 항목 비율.
5. **자동 예측 MOS**(보조, 회귀 검사용): 공개 MOS 예측 모델(예: UTMOS 계열)로 매 빌드마다 점수를 내 급락만 감시한다. 판정 근거로는 쓰지 않는다(한국어 정확도 미검증).

| 지연 영향 | PVC는 IVC·기본 음성보다 느리다. | [문서] `concepts/latency` |

### 2-2. 측정법 [제안]
1. **SECS(객관)**: 화자 임베딩 모델(예: ECAPA-TDNN, WavLM 기반 화자 검증 모델 중 하나로 고정)로 "원화자 실제 녹음(참조에 안 쓴 문장)"과 "클론 생성 음성"의 임베딩 코사인 유사도를 잰다. 같은 화자의 다른 실제 녹음끼리 잰 값을 **상한 기준**으로 함께 보고한다.
2. **SMOS(주관)**: 원화자 실제 녹음 1개와 생성 음성 1개를 들려주고 "같은 사람 같은가" 5점 척도. 청취자 20명 이상, 화자당 문장 10개 이상.
3. **화자 검증 수락률**: 같은 임베딩 모델의 동일 화자 판정 임계값(EER 지점)을 넘는 생성 음성 비율.
4. **조건별 분리 보고**: 참조 길이(10초/30초/1분/2분/3분) × 녹음 조건(깨끗/노트북 마이크/잡음) × 생성 언어(같은 언어/교차 언어) × 말투(낭독/대화/감정).
   - **ElevenLabs 비교는 축소안**(대표 결정 2026-11-21): 무료 즉시 클로닝 3건 안에서만 한다. ElevenLabs는 **"깨끗한 녹음 · 1분 참조" 한 조건 × 화자 3명**만 잰다. 나머지 조건(참조 길이·녹음 조건 변형)은 우리 엔진만 재고, ElevenLabs 대비가 아니라 우리 1분 조건 대비 하락 폭으로 판정한다(2-3 표).
5. **자연스러움 동시 측정**: 클론 음성도 1절 MOS를 같이 잰다. 유사도만 높고 부자연스러운 경우를 막는다.

| 더빙 화자 유사도 | SECS ≥ ElevenLabs 더빙(기본 설정 7) − 0.03 |

## 5. 테스트 계획 초안 — 브라우저별 녹음 포맷 · 마이크 권한 거부 (프론트팀 요청)

전제: 우리 녹음 구현안은 `03-frontend` 1-3(권한은 녹음 버튼 누를 때 요청, `MediaRecorder`가 `audio/webm;codecs=opus` → `audio/mp4` 순서로 선택, 3:00 자동 정지, 10MB·길이 검사 클라이언트+서버), 화면 상태는 `02-design` 3-6절 S0~S6 이름을 그대로 쓴다. 대상은 우리 PoC 빌드다(ElevenLabs 앱에서는 녹음하지 않는다).

| REC-03 | MP3 변환 | 서버 변환 결과 확인(백엔드 기본안 MP3 192kbps) | 192kbps, 길이 차 ≤ 0.1초 |
| REC-04 | 길이 메타데이터 | 녹음 파일 길이를 `decodeAudioData`와 `<audio>.duration` 양쪽으로 읽음 | 두 값 차 ≤ 0.1초. `Infinity`/0이 나오면 클라이언트는 `decodeAudioData` 값을 써야 함 |
| REC-05 | 3:00 자동 정지 | 정지 안 누르고 계속 녹음 | 3:00 ± 0.5초에 정지, S4로 이동, 2:45 경고 문구 표시 |

| REC-09 | 녹음 중 이탈 | 녹음 중 탭 닫기·새로고침·뒤로가기 | 이탈 확인 창. 녹음본 유실 없음(데이터 손실 방지 규칙) |

### 5-3. 마이크 권한 거부 시나리오
| ID | 상황 | 재현 방법 | 기대 결과(우리 앱) |
|---|---|---|---|
| PRM-01 | 페이지 진입 | 녹음 화면 진입만 함 | 권한 팝업 안 뜸, `permissions.query` 결과 `prompt` 유지(ElevenLabs도 진입 시 요청 안 함 — [타팀] `03-frontend` 1-1) |
| PRM-02 | 첫 요청에서 거부 | S1 안내 카드 → 허용하기 → 브라우저 팝업에서 차단 | `NotAllowedError` → S1x "마이크 사용이 막혀 있어요" + 해결 단계 + **파일 올리기 전환이 주 버튼** |
| PRM-03 | 이전에 사이트 차단 | 사이트 설정에서 마이크 차단 후 녹음 누름 | 팝업 없이 즉시 S1x. 브라우저별 해제 방법 안내가 맞는지 확인 |
| PRM-04 | 팝업 무시·닫기 | 팝업을 X로 닫거나 바깥 클릭, 여러 번 반복 | S1 대기 상태에 갇히지 않음. 반복해서 닫으면 브라우저가 자동 차단할 수 있음(실측) → S1x로 이동 |
| PRM-05 | OS 수준 차단 | Windows 개인정보 설정 마이크 끔 / macOS 시스템 설정 브라우저 마이크 끔 / iOS 설정 Safari 마이크 끔 | 오류 이름 기록(`NotAllowedError` 또는 `NotReadableError`, 실측). OS 설정 안내 문구 표시 |
| PRM-06 | 장치 없음 | 마이크 없는 PC 또는 장치 비활성 | `NotFoundError` → "연결된 마이크를 찾지 못했어요" |
| PRM-07 | 장치 점유 | 다른 앱(화상회의)이 마이크 독점 | `NotReadableError` → 원인 안내 + 다시 시도 |
| PRM-08 | 보안 연결 아님 | http로 접속(로컬 IP 등) | `navigator.mediaDevices`가 없음 → "https에서만 녹음" 안내. 스크립트 오류로 화면이 깨지지 않음 |
| PRM-09 | iframe 삽입 | `allow="microphone"` 없는 iframe 안에서 녹음 | `NotAllowedError` → S1x. (위젯 임베드 대비) |
| PRM-10 | 녹음 중 권한 회수 | 녹음 중 주소창에서 마이크 차단 / USB 마이크 뽑기 | 트랙 `ended` 감지 → 녹음 중단, 그때까지 녹음본 보존, 안내 표시 |
| PRM-11 | 일회성 허용 | Firefox "이번만", Safari 매 방문 재요청, Chrome "이번 방문에만" | 다음 방문에 다시 S1을 정상으로 거침 |
| PRM-12 | 인앱 브라우저 | 카카오톡 링크로 열기 | 미지원이면 "외부 브라우저로 열기" 안내 + 파일 올리기 대체 경로 |
| PRM-13 | 권한 상태 조회 미지원 | `permissions.query({name:'microphone'})` 미지원·예외 브라우저 | 조회 실패해도 녹음 버튼 흐름은 정상(조회는 표시용) |
| PRM-14 | 접근성 | 키보드만으로 S1 → S1x → 파일 업로드 전환 | 포커스 이동, 오류 문구 `role="alert"` 낭독(`02-design` 3-6 공통 규칙) |

- 결과 기록: 브라우저·OS·버전, 실제 오류 이름(`err.name`), 화면 상태(S 코드), 스크린샷.
- 합격선 [제안]: PRM 전 케이스에서 **화면 멈춤 0건, 녹음본 유실 0건, 모든 거부 상태에서 파일 업로드로 1번 클릭에 전환**.

## 8. 확인 못 한 것 정리

- 제안한 측정 모델(UTMOS, ECAPA-TDNN·WavLM 화자 검증, SyncNet)의 한국어 성능은 확인 못 함.

### 9-3. 음성 전처리(블라인드 유지)

### 9-6. 분석 방법
- MOS 평균과 95% 신뢰구간은 평가자와 문장 두 축으로 부트스트랩해 낸다(한쪽만 쓰면 구간이 좁게 나옴).
- 시스템 간 차이: 같은 문장끼리 짝지은 Wilcoxon 부호순위 검정, 여러 쌍 비교라 Holm 보정. 짝비교 선호율은 이항 검정.
- 묶음별(숫자, 혼용, 대화체, AICC) 결과를 따로 낸다. 마케팅 메시지는 "전체 1위"보다 "숫자·상담 문장에서 강함"처럼 묶음 단위 근거가 더 방어하기 쉽다.
- 판정: 차이의 95% 신뢰구간이 0을 포함하면 "차이 없음"으로 보고한다(순위만 따로 내지 않는다).
